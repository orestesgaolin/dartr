# dartr_resolver: how to port a resolver file against the core

This crate is the body resolution of the analyzer (design
`docs/design/semantics.md` wave C). Units C3–C10 port the Dart resolver files
into it in parallel. This document is the contract between the core
(`ResolverVisitor`) and those files.

## 1. Layout

| module | Dart source | owner |
|---|---|---|
| `resolver/mod.rs` | `generated/resolver.dart` (`ResolverVisitor` state and helpers) | core (C2) |
| `resolver/{expressions,statements,declarations,collection_elements,patterns}.rs` | `generated/resolver.dart` (the `visitX` methods) | core (C2) |
| `resolver/type_analyzer_impl.rs` | `generated/resolver.dart` (`TypeAnalyzer` / `NullShortingMixin` members) | core (C2) |
| `generated/dispatch.rs` | `ast.dart` (`accept`, `resolveExpression`, `resolveElement`, `resolvePattern`) | generated by `tools/codegen/gen_resolver_dispatch.py` |
| `static_type_analyzer.rs`, `element_resolver.rs`, `error_detection_helpers.rs` | `generated/*.dart` | core |
| `body_inference_context.rs`, `flow_analysis_visitor.rs`, `shared_type_analyzer.rs`, `type_analyzer_options.rs` | `dart/resolver/*.dart` | core |
| `simple_identifier_resolver.rs`, `lexical_lookup.rs`, `this_lookup.rs`, `type_property_resolver.rs`, `resolution_result.rs` | `dart/resolver/*.dart` | core |
| `variable_declaration_resolver.rs`, `function_expression_resolver.rs`, `yield_statement_resolver.rs` | `dart/resolver/*.dart` | core |
| `scope.rs`, `element_walker.rs`, `element_binding_visitor.rs`, `scope_context.rs`, `resolution_visitor.rs`, `named_type_resolver.rs`, `ast_rewrite.rs`, `record_type_annotation_resolver.rs` | `dart/element/scope.dart`, `dart/resolver/*.dart` | C1 |
| `library_analyzer.rs` | `dart/analysis/library_analyzer.dart` | C11 |
| every other `*_resolver.rs` | the Dart file of the same name | C3–C9 (stubs today) |

Every file starts with `// Dart source: <path>`; functions keep the Dart
method names in snake case. A stub file says `STUB (unit Cx)` at the top.

## 2. Passes and results

`library_analyzer::analyze_library` resolves the units of a library in
parallel (rayon). Each unit gets a clone of its parsed `Ast` (resolution
rewrites nodes) and a fresh `LocalArena` (local elements and local types).
The passes per unit (Dart `LibraryAnalyzer._resolveFile`):

1. `element_binding_visitor::bind_unit` — `declared_fragment` of each
   declaration; local fragments and elements in the local arena.
2. `resolution_visitor::resolve_unit` — scopes, type annotations
   (`annotation_type`), scope lookup results of identifiers
   (`ResolverTables.scope_lookup_result`), AST rewrites.
3. `ResolverVisitor` — static types, elements, inference, flow analysis.

Results (what Dart writes into AST nodes):

- `ResolutionTables` (`dartr_element`): `static_type`, `element`,
  `declared_fragment`, `invoke_type`, `type_arg_types`, `param_element`,
  `annotation_type`, `read_/write_element`, `read_/write_type`, ... keyed by
  `NodeId`.
- `ResolverTables` (`tables.rs`): resolver-private node data. Add a field
  there when your file needs a Dart node field that is neither a public
  result nor computable from the syntax; document the Dart field.
- Diagnostics: `ResolverVisitor::report`.

`Driver::analyze_library(file, options)` (`dartr_driver::analysis`) runs this
for a linked library.

## 3. The core API that resolver files use

A resolver file is a set of free functions that take
`rv: &mut ResolverVisitor<'_>` (Dart: a helper class with a `_resolver`
field). The entry point of a node kind is `visit_<kind>(rv, node, context)`
(the Dart `ResolverVisitor.visitX` together with the Dart resolver class);
the core's `visit_<kind>` method calls it.

### Syntax

- `rv.ast: &mut Ast` — `rv.ast[node].field`, `rv.ast.parent(n)`,
  `rv.ast.cast::<T>(n)` (Dart `is`/`as`), `rv.ast.list(list)`,
  `rv.lexeme(token)`, `rv.ast.offset(n)` / `length(n)`.
- AST getters computed from syntax (`inGetterContext`, `unParenthesized`,
  ...): `ast_ext.rs`. Element getters (`isLate`, `variable type`,
  `getField`): `element_ext.rs`.

### Expressions

| Dart | Rust |
|---|---|
| `resolver.analyzeExpression(e, SharedTypeSchemaView(ctx)); e = resolver.popRewrite()!;` | `let e = rv.resolve_expression(e, ctx);` (returns the node now in the slot) |
| `resolver.analyzeExpression(e, schema)` (result needed) | `let r = rv.analyze_expression_node(e, schema);` then `rv.pop_rewrite()` |
| `operations.unknownType` / `UnknownInferredType.instance` | `TypeId::UNKNOWN` |
| `node.recordStaticType(t, resolver: resolver)` | `rv.record_static_type(node, t)` (calls `flow.handleExit()` for a bottom type) |
| `node.setPseudoExpressionStaticType(t)` | `rv.set_static_type(node, t)` |
| `node.staticType` / `typeOrThrow` | `rv.static_type(n)` / `rv.type_or_throw(n)` |
| `node.element = e` / `node.element` | `rv.set_element(n, Some(ElemRef::Base(e)))` / `rv.element(n)` |
| `resolver.replaceExpression(old, new, parent: p)` | create `new` with `rv.ast.add(...)` (it adopts its children), then `rv.replace_expression(old, new, Some(p))`; pass the old parent when `new` is the new parent of `old` |
| `insertGenericFunctionInstantiation(e, contextType:)` | `rv.insert_generic_function_instantiation(e, ctx)` |
| `_insertImplicitCallReference(e, contextType:)` | `rv.insert_implicit_call_reference(e, ctx)` |
| `node.accept(resolver)` / `node.visitChildren(resolver)` | `rv.visit_node(n)` / `rv.visit_children(n)` |
| `checkUnreachableNode(n)` | `rv.check_unreachable_node(n)` |

Rewrites: side tables are keyed by `NodeId`, so a new node starts with empty
entries; record its results after `replace_expression`.

### The shared type analyzer

`ResolverVisitor` implements `dartr_flow::type_analyzer::TypeAnalyzer` (the
`TypeAnalyzer` mixin; bodies in `dartr_type_analyzer`). Call the mixin
methods with the trait in scope: `use dartr_flow::type_analyzer::TypeAnalyzer;`
then `rv.analyze_yield_statement(node.upcast(), expression, is_star)`,
`rv.analyze_if_statement(...)`, `rv.analyze_await_expression(...)`, ... The
mixin's errors are recorded and converted into diagnostics in report order
(`shared_type_analyzer.rs`).

### Types, elements, inference

- `rv.ctx: Ctx<'a>` (with the unit's local arena), `rv.type_system:
  TypeSystem<'a>` (`is_subtype_of`, `is_assignable_to`, `least_upper_bound`,
  `flatten`, ...), `dartr_typesystem::TypeExt` on `ctx` (`as_instance_of`,
  `type_arguments`, `instantiate_function_type`, ...), the type provider
  `rv.ctx.tp`.
- Members: `dartr_typesystem::member` (`type_`, `return_type`,
  `base_element`, `is_static`, ...), inheritance:
  `dartr_typesystem::inheritance_manager3::InheritanceManager3::new(rv.ctx)`.
- `rv.infer_function_type_instantiation(context, fn_type, error_node,
  generic_metadata)`; `GenericInferrer` in `dartr_typesystem`.
- Property lookup on a type: `type_property_resolver::resolve(rv,
  PropertyQuery { .. })`.
- Local elements: created by the element binding pass in
  `rv.ctx.local.unwrap().store` (append-only through `&self`); a local
  variable's type is set with `element_ext::set_local_variable_type` (Dart
  `element.type = ...`). Never mutate a linked (frozen) element.

### Flow analysis

`rv.flow_analysis: FlowAnalysisHelper` (Dart `flowAnalysis`):
`rv.flow()` (Dart `flow`, panics outside a body), `rv.flow_analysis.flow`
(Dart `flow?`), `get_expression_info(Some(e))` / `store_expression_info(e,
info)`, `write(ast, node, variable, type, info)` (use it, not `flow.write`),
`local_variable_type(...)`. The `FlowAnalysis` trait must be in scope:
`use dartr_flow::flow_analysis::FlowAnalysis;`.

### Enclosing declarations, bodies

`rv.enclosing_class`, `rv.enclosing_extension`, `rv.enclosing_function`,
`rv.this_type()`, `rv.effective_this_type()`, `rv.body_context()` /
`body_context_mut()` (Dart `bodyContext`), `rv.resolve_function_body(body,
imposed_type)` (Dart `body.resolve(resolver, imposedType)`),
`rv.with_flow_analysis(node, |rv| ...)`.

### Diagnostics

`rv.report(rv.at(diag::xyz(args), node))` (Dart
`diagnosticReporter.report(diag.xyz.withArguments(...).at(node))`);
`rv.at_token(d, token)`; type and element arguments:
`dartr_element::diagnostics::{type_arg, element_arg}`. Checks of wave D
(`checkForArgumentTypeNotAssignable`, `BoolExpressionVerifier`, ...) have
hooks in `error_detection_helpers.rs`; call the hook at the Dart call site
even if it reports nothing yet.

## 4. Porting one file: steps

1. Read the Dart file and the `visitX` methods of `generated/resolver.dart`
   for the node kinds it owns.
2. Replace the stub functions in the Rust module; keep their signatures
   (the core calls them). Add Dart helper methods as private functions with
   the Dart names.
3. Port the `visitX` body from `resolver.dart` into your entry point (the
   core does not do anything else for that node kind; the stub file names
   the entry points).
4. If you need a core capability that is missing, add it to
   `resolver/mod.rs` in a small, documented method and say so in your
   report.
5. Measure: `difftest resolved --kinds <your node kinds>` and
   `difftest resolved-el` (see `crates/dartr_difftest`).

## 5. Example: `yield_statement_resolver.rs`

The full port of `yield_statement_resolver.dart`. The core calls the entry
point from `ResolverVisitor::visit_yield_statement` after
`check_unreachable_node`:

```rust
/// Dart `ResolverVisitor.visitYieldStatement(node)` (after
/// `checkUnreachableNode`) = `YieldStatementResolver.resolve(node)`.
pub fn visit_yield_statement(rv: &mut ResolverVisitor<'_>, node: Id<YieldStatement>) {
    match rv.body_context() {
        Some(body_context) if body_context.is_generator => resolve_generator(rv, node),
        _ => resolve_not_generator(rv, node),
    }
}

/// Dart `_resolve_generator`.
fn resolve_generator(rv: &mut ResolverVisitor<'_>, node: Id<YieldStatement>) {
    let expression = rv.ast[node].expression;
    let is_yield_star = rv.ast[node].star.is_some();
    // The shared type analyzer (TypeAnalyzer mixin).
    rv.analyze_yield_statement(node.upcast(), expression, is_yield_star);
    // The expression may have been rewritten: read it again from the node.
    rv.pop_rewrite();
    let expression = rv.ast[node].expression;
    if is_yield_star {
        rv.nullable_dereference_expression(
            diag::unchecked_use_of_nullable_value_in_yield_each(),
            expression,
            None,
        );
    }
    // Dart `bodyContext.addYield(node)`.
    let expression_type = rv.type_or_throw(expression);
    let ts = rv.type_system;
    if let Some(body_context) = rv.body_context_mut() {
        body_context.add_yield(&ts, expression_type, is_yield_star);
    }
    let body_context = rv.body_context().cloned().expect("body context");
    check_for_yield_of_invalid_type(rv, &body_context, node, is_yield_star);
    check_for_use_of_void_result(rv, expression);
}

/// Dart `_resolve_notGenerator`.
fn resolve_not_generator(rv: &mut ResolverVisitor<'_>, node: Id<YieldStatement>) {
    let expression = rv.ast[node].expression;
    let expression = rv.resolve_expression(expression, TypeId::UNKNOWN);
    let d = if rv.ast[node].star.is_some() {
        diag::yield_each_in_non_generator()
    } else {
        diag::yield_in_non_generator()
    };
    let d = rv.at(d, node);
    rv.report(d);
    check_for_use_of_void_result(rv, expression);
}
```

The diagnostic checks (`check_for_yield_of_invalid_type`,
`check_for_use_of_void_result`) are in the file; see the source.

## 6. Rules

- Determinism (design §2.5): `IndexMap`/`IndexSet` for iterated maps, never
  sort or hash-iterate by ids; `cargo clippy -p dartr_resolver --no-deps
  --all-targets -- -D warnings` (the crate has `clippy.toml`).
- Do not panic on erroneous code; a panic is caught per unit by the library
  analyzer and loses the whole unit.
- Body resolution never mutates linked elements (frozen stores are shared
  between threads); it writes only to its tables, its local arena and its
  diagnostics.
- Tests: integration tests that analyze Dart source through
  `Driver::analyze_library` and check concrete results; parity numbers from
  `dartr_difftest`.

## 7. Open points of the core

- Linking calls the resolver through a hook (C10): `dartr_link` defines
  the traits `link::LinkResolver` / `LinkResolverSession` and the request
  `link::ExpressionRequest`; `dartr_link::link::link_cycle` takes a
  `&dyn LinkResolver`; the driver passes `dartr_driver::link_resolver::
  ResolverForLinking`, which calls `ast_resolver::LinkResolution` (Dart
  `summary2/ast_resolver.dart`). Neither `dartr_link` nor `dartr_resolver`
  depends on the other. `ast_resolver` resolves one expression in a copy
  of its unit (the linker shares the parsed units): `bind_subtree`, the
  resolution visitor in the initializer scope, then the resolver visitor.
  The types of fields and top-level variables are inferred on demand
  (Dart `PropertyInducingElementImpl.type` calls `typeInference`):
  `dartr_element::type_inference` keeps the hook of the linking thread,
  and the readers of variable and accessor types (`member::type_`,
  `member::return_type`, `element_type::executable_type`,
  `element_ext::variable_type`, ...) call `ensure_*` when the slot is
  empty. A new reader of a field, top-level variable or accessor type in
  code that runs during linking must call `ensure_property_type` /
  `ensure_accessor_return_type` first.
- Patterns, switch statements and expressions, if-case statements, pattern
  variable declarations and pattern assignments are ported
  (`pattern_resolver.rs`, `resolver/patterns.rs`,
  `list_pattern_resolver.rs`). They read from the binding passes:
  `declared_fragment` of each `DeclaredVariablePattern` (a
  `BindPatternVariable` element; its fragment has `pattern.node` and
  `pattern.join`), the join variables (`JoinPatternVariable`, with
  `pattern.variables`, `inconsistency`, `references`), `element` of each
  `AssignedVariablePattern`, `annotation_type` of type annotations and
  `element` of `NamedType`s, and the tables
  `ResolverTables::guarded_pattern_variables` (Dart
  `GuardedPatternImpl.variables`) and `ResolverTables::switch_case_group_variables`
  (Dart `SwitchStatementCaseGroup.variables`, keyed by the last member of
  the group). When the two tables are not written, the pattern resolver
  computes them from the bound variables. If-case collection elements and
  pattern for-in loops (`typed_literal_resolver.rs`, `for_resolver.rs`) can
  use `pattern_resolver::guarded_pattern_variables`.
- `checkPatternNeverMatchesValueType` needs `TypeSystem.canBeSubtypeOf`
  (not ported in `dartr_typesystem`): `pattern_never_matches_value_type` is
  not reported yet.
- Constants (wave D, D1–D3, `src/constant/`): `library_analyzer` computes
  the constants of the library (`_computeConstants`, results in
  `ResolvedLibrary::constants`) and runs the constant verifier per unit,
  with switch exhaustiveness. The evaluator reads resolved unit ASTs, not
  the linker's `ConstExprs`: the units of other libraries come from an
  `ExternalUnitCache` (resolved on demand); see `constant/mod.rs`. The
  other library-wide steps (error verifier, imports, ignore comments) are
  other wave D units.
- The type algorithms (`isSubtypeOf`, `isNonNullable`, `UP`, ...) panic
  with `StackOverflowError` at a fixed recursion depth
  (`dartr_typesystem::recursion_guard`), where Dart overflows its stack
  (recursive bounds such as `X extends FutureOr<X>`). The library analyzer
  catches the panic per unit (`ResolvedUnit::panic`).
- The linker does not set `LibraryFragment.enclosing_fragment` for part
  files; `LibraryScopes` finds the parent of a part from the `part`
  directives instead.

## 8. Measuring

```sh
cargo build --release -p dartr -p dartr_difftest
target/release/difftest resolved-el <dirs or dart: URIs> --no-diagnostics
target/release/difftest resolved <dirs> --no-diagnostics --kinds IntegerLiteral,IsExpression
```

Both modes print a per-kind table (oracle entries, entries dartr matches
exactly, parity). A batch is killed after 60 s + 10 s per file
(`--timeout-per-file`). Run every corpus command with a time limit, for
example `perl -e 'alarm 1800; exec @ARGV' target/release/difftest ...`.
